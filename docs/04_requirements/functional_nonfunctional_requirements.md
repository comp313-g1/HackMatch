# Functional and Non-Functional Requirements Document

## Overview

This document translates the [canonical user stories](../02_user_stories/user_stories.md) and [MVP definition](../03_mvp/mvp_definition.md) into **85 functional requirements and 24 non-functional requirements (109 total)**. Current story IDs are authoritative; older proposal/issue numbering will be reconciled separately.

The FR rows explicitly distinguish **69 MVP**, **15 Should-Have post-MVP**, and **1 May-Have future** requirement. Quality requirements apply to delivered features only; references to a later feature do not make it an MVP dependency. FR-064 basic status alerts and FR-079 basic administrative records ship in MVP; the notification centre/audit-query interface ship later. Future US-016 has no implementation requirements yet because its algorithm is uncommitted. US-029/FR-017 are a future design outline, not a release promise.

Public roles are defined in [Roles and Personas](../01_roles_and_personas/roles_and_personas.md): PART and ADMIN accounts, contextual team ownership, unauthenticated Visitor, and external Organizer/academic stakeholders. Detailed user stories remain in Markdown; the later Word timeline will cover Must-Have MVP phases only.

<a id="policy-register"></a>

### Policy Register and Evidence Status

Confirmed direction: email OTP expires after **10 minutes**; **5 incorrect OTP attempts lock the account for 15 minutes**, including OAuth sign-in. Responsive browsers include tablet/iPad and both phone orientations. Event submissions by any verified PART are private until ADMIN approval; only Verified records enable recruitment. The team confirmed **20 Must-Haves** as MVP and **7 Should-Haves** after MVP. These decisions override conflicting earlier wording.

The defaults below are retained or repaired proposals for this expanded product. They form one consistent candidate policy, but must not be described as professor-prescribed numbers or demonstrated production performance.

| Policy | Consistent proposed choice | Confirmation still needed |
|---|---|---|
| R-01 Capacity | Use official event min/max, including owner; no platform-wide 4-person/2–6 cap. Unknown rules keep an event pending. | Approve this official-rules policy and how events with no published team limits will be supported; no numeric fallback is invented. |
| R-02 Recruitment lifecycle | 48-hour invitations; one pending invite per slot and candidate/team; at most 3 pending applications/event; pitch 500 and application note 250 characters. Both join routes cancel the participant other event requests. Non-owner exit/removal and owner disband are pre-lock only; no ownership transfer/unlock. | Team sign-off on these retained/default policy details and restrictive invite quota. |
| R-03 Identity defaults | Retain Google/GitHub for PART, mandatory email OTP for every login, verified personal or academic emails. Retain 24-hour verification, 60-minute recovery, 15-minute access/7-day renewal, registration password policy. Proposed resend guard: one send/minute and five/hour per account/purpose. | Confirm non-professor numeric identity/send settings and provider deployment setup; no OAuth exemption is pending. |
| R-04 Matching | Preserve skill/goal/hours rule-based scoring; define bounded components and equal one-third weights as the proposed baseline, with capped 1.2 role multiplier and explicit goal adjacency. | Approve/calibrate weights with representative scenarios; no claimed prediction accuracy. |
| R-05 Quality targets | Preserve measurable performance/load, availability/recovery and coverage ambitions, and define repeatable acceptance protocols below. Include mobile/tablet browsers. | Approve hosting budget, benchmark environment and attainable semester acceptance thresholds. Current values are proposed targets, not measured guarantees; no release claim until demonstrated. |
| R-06 Data lifecycle | Proposed 30-day live PII deletion, pseudonymized history, secret-free action records, and deletion replay after restore. | Determine applicable obligations and explicit backup/log retention/deletion periods before real-user production; synthetic data until resolved. |

Event verification maintains trusted records only. Ticketing, payments, judging, attendee registration, full event scheduling and organizer self-service are outside this release. Advanced candidate search, history, workspace, export, reporting, notification centre and audit querying retain their expanded product scope but follow the post-MVP categories.

### Measurement Convention

Before acceptance, record deployment resources, build, test data distribution, browser/device versions and network profile. Timing starts/ends as stated in each NR; publish p95 and error counts, not a single best run. Load/hosting targets in R-05 remain proposed until confirmed and measured. Security and integrity acceptance is mandatory regardless of traffic target. Technical architecture may choose implementations satisfying these observable contracts; no library/vendor is mandated here.

### Feature Area 4: Rule-Based Matching

Covers deterministic candidate compatibility scoring, skill gap analysis, schedule weighting, and explainable recommendation rendering.

| ID | Requirement | Related User Stories | Acceptance Conditions |
|---|---|---|---|
| <a id="fr-043"></a>**FR-043** | **MVP:** The system shall compute deterministic candidate compatibility. | [US-015](../02_user_stories/user_stories.md#us-015) | Proposed policy R-04: score = 100 * (S + G + H) / 3, where components are in [0,1]; display one decimal, rank by unrounded score then handle/internal identifier. No missing input is invented: missing component data scores 0. Component weights are a proposed baseline, not professor-approved or predictive accuracy claims. |
| <a id="fr-044"></a>**FR-044** | **MVP:** The system shall compute bounded skill coverage. | [US-015](../02_user_stories/user_stories.md#us-015) | S is matched required tags / required tag count, capped at 1 after a 1.2 multiplier when declared primary role matches the slot. Empty required tags give S=1 before the cap. This is required-skill coverage, not Jaccard similarity. Example: 2 of 4 tags and role match gives S=0.6. |
| <a id="fr-045"></a>**FR-045** | **MVP:** The system shall compute goal and commitment components. | [US-015](../02_user_stories/user_stories.md#us-015) | G=1 for identical goals, 0.5 for Learning/Project Completion or Project Completion/Competitive, and 0 for Learning/Competitive. H=min(candidate hours / team requested hours,1); if requested hours=0, H=1. Missing data scores 0. Example S=0.6,G=1,H=0.5 yields 70.0. Defaults remain subject to R-04 review. |
| <a id="fr-046"></a>**FR-046** | **MVP:** The system shall exclude ineligible candidates. | [US-015](../02_user_stories/user_stories.md#us-015) | Only active PART users Looking for Team in the same Verified event enter rankings. Exclude every confirmed member for that event, including members of unlocked non-full teams; revalidate eligibility again before invitation/acceptance. |
| <a id="fr-047"></a>**FR-047** | **MVP:** The system shall explain ranked recommendations. | [US-015](../02_user_stories/user_stories.md#us-015) | Owner sees descending scores with skill, goal, and hours contributions, tie-breaking defined by FR-043, and self-declared-data notice. No candidates produces an empty state; internal identifiers are not displayed. |
| <a id="fr-048"></a>**FR-048** | **MVP:** The system shall start invitations from recommendations. | [US-015](../02_user_stories/user_stories.md#us-015), [US-017](../02_user_stories/user_stories.md#us-017) | An owner can select an eligible recommended candidate and prefill the invitation for the selected slot. Confirmation executes the same authorization, capacity, quota and current-eligibility checks as other invitation entry points; no duplicate invitation results. |

| <a id="nr-019"></a>**NR-019** | Browser compatibility. | All | Proposed support matrix: latest two stable major versions available at release freeze of desktop Chrome/Firefox/Edge/Safari, plus iPadOS/iOS Safari and Android Chrome. Record exact OS/browser versions and test the NR-017 tasks/orientations on each; no blocked core task, lost input, or inaccessible control is allowed. Emulation supplements, not replaces, recorded device/browser verification; matrix confirmation is R-05. |
