# HackMatch Sprint Evidence

## Evidence categories

Map work to the six assessment categories:

1. Sprint goal and backlog;
2. user stories and diagrams;
3. Git repository and commit history;
4. initial working prototype;
5. debugging and testing;
6. Sprint 1 demonstration.

## Required evidence records

For each completed story or task, capture:

- story/task ID;
- owner and reviewer;
- branch and pull request;
- acceptance criteria demonstrated;
- test case IDs and result;
- positive and negative scenarios;
- validation and authorization scenarios;
- screenshots, logs, API responses, or automated test output;
- known limitations;
- date of review.

## Demo coverage

The demo should show a working path through:

- verified account registration or approved sign-in;
- mandatory email OTP;
- profile and event discovery;
- event submission and ADMIN approval gating;
- availability and team listing;
- application and invitation routes;
- membership/capacity protection;
- roster lock;
- responsive/accessibility evidence;
- debugging and retesting evidence.

Do not claim a feature is complete because a screen exists. The evidence must demonstrate behavior, error handling, and the relevant authorization boundary.

## Output

Produce a concise evidence matrix:

```markdown
| Rubric | Story/task IDs | Demonstration or artifact | Test result | Owner | Reviewer | Gap |
|---|---|---|---|---|---|---|
```

Report incomplete evidence separately from incomplete implementation. A known limitation should be documented for the presentation rather than hidden.
